# ADR-0007 · 课程主线改为「六层能力叠加」，案例改为「建造」而非「批判」

**状态**：已采纳 · 2026-09-16（取代 DESIGN.md §2 的章节编排与 §4 的案例模型）

## 背景

DESIGN.md 的初版编排是：第 1 章诊断一个写坏了的看板（`v0`，内含 12 个「病灶」），
第 2–6 章每章修掉其中几个，最终产出 `v6`。章节主题依次为
感知 / 网格 / 引擎 / 自适应 / 美感 / 稳健。

实现并试读之后，这个结构暴露了三个问题：

1. **章节之间没有因果关系。** 「网格」和「引擎」谁先谁后，从内容上说不出理由 ——
   它们只是六个并列的主题，被一个案例串在一起。读者学完第 3 章，
   并不会觉得第 4 章是「必然的下一步」。
2. **案例与章节是两张皮。** 病灶编号（#2 #4 #5…）散落在各章，
   每章开头都要重新回顾一遍案例才能接上，回顾成本高于收益。
3. **「全程分析错误案例」教出来的是挑毛病，不是动手。**
   读者反复看到的是「这里做错了」，而不是「这里应该怎么长出来」。

## 决策

改为**六层能力叠加**：

```
内容层 → 间距层 → 尺度层 → 结构层 → 视觉层 → 适应层
```

这个顺序不是分类，是**依赖关系**：

- 没有确定的内容与行长，谈不上间距；
- 没有分组关系，谈不上把值收敛成标尺；
- 没有标尺，谈不上在平面上安排结构；
- 没有结构，视觉层级只能靠边框和阴影代偿；
- 没有前五层，适应层就只能靠越来越多的媒体查询打补丁。

案例模型相应重写：`v0..v6` → `stage0..stage6`。
**`stage0` 不是「写坏了的页面」，而是「还没有布局的页面」** ——
真实数据、语义正确的 HTML、零布局 CSS。常规流已经让它在 320px 到 4K 上都能读。
之后每一章加一层能力，六层之后成为可交付的看板。

指标从 4 项扩到 6 项，并且**每一项都指定归属层**：

| 指标 | 归属层 | stage0 → stage6 |
|---|---|---|
| 行长 (ch) | 1 内容层 | 138 → 64 |
| 分组比 | 2 间距层 | 1.0 → 2.0 |
| 取值种类 | 3 尺度层 | 3 → 17 |
| 可达性问题数 | 4 结构层 + 6 适应层 | 6 → 0 |
| 层级分 | 5 视觉层 | 0.05 → 0.84 |
| CLS | 6 适应层 | 0.31 → 0.004 |

## 理由

1. **编排有了可检验的标准。** 判据是：**每一层都必须能推动一项指标**。
   推不动任何指标的层，要么不该存在，要么讲错了地方。
   这条判据直接决定了小节在章节之间的迁移（例如「DOM 顺序」从原「稳健」章
   迁到结构层 —— 顺序本来就是结构的一部分，不是事后的可达性补救）。
2. **每章自带案例上下文。** `CaseStage.svelte` 挂在每章开头，
   一条窄入口写明「现在是哪一阶段 → 这一章要到哪一阶段」，
   点开是一个 `<dialog>` 弹窗：上一阶段的**实时**看板预览、本章将要加上的能力、本层负责的指标。
   做成弹窗而不是常驻展开，是因为上下文应当**随时可查**，而不该占掉每章开头的一屏 ——
   读第二遍的人不该每次都被自己看过的内容挡一次路。
   读者因此不需要回到案例馆，也不需要记住十二个编号。
3. **叙事从「修」变成「长」。** 每章末尾的案例小节展示的是一次**纯增量的 diff**
   （全课程只有一次覆盖：stage3 把 KPI 区的 `display: flex` 换成 `display: grid`，
   并在 §4.1 解释为什么）。读者带走的是「加一层能力」的动作，不是「挑一个毛病」的眼光。
4. **跨章承诺可以被兑现。** §4.5 为了补足分隔加了全页唯一一条 `border`，
   §5.6 在面色接管之后正式撤掉它。前面欠下的，后面必须还 ——
   这是六层结构相对六个独立主题的直接收益。

## 代价

- 六章正文全部重写（约 4500 行内容模块），旧的 `ch1-perception` … `ch6-robust` 删除。
- `case.ts` 的数据模型重写，`Dashboard.svelte` 的 CSS 改为**严格叠加式**
  （`stage0` 零布局 CSS，每层只追加 `[data-s='N']` 及以上的规则）。
- 自检清单、决策树、案例馆表格、门户页的全部小节交叉引用需要重编号。

## 连带的实现约束

- **DOM 顺序从 `stage0` 起就按业务重要度降序写定**，因此全课程没有任何一处 `order`。
  §4.4 讲的是「如果当初写错了，代价有多大」，而不是「现在来修」。
- `Dashboard.svelte` 的 CSS 必须可加不可减：任何一层的规则都不允许改写更早的层，
  唯一的例外必须在正文里显式标注并解释。
- 指标数值写在 `case.ts` 的 `stages[].metrics` 里，是**度量函数在各阶段的实测结果**，
  与 `src/lib/` 的纯函数实现一致；单元测试覆盖这些函数，而不是这些数值。
