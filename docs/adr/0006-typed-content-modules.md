# ADR-0006 · 用带类型的结构化 TS 模块承载内容，而不是 MDX

**状态**：已采纳 · 2026-09-16（取代 DESIGN.md §6 中「内容集合 + MDX」的初始设想）

## 背景

DESIGN.md 最初计划用 MDX 写正文，靠 `check-i18n-parity` 脚本比对中英两份文件的结构。

## 决策

改用带类型的结构化模块：每个面向用户的字符串都是 `L = { zh: string; en: string }`，
块类型是一个判别联合（`p` / `h` / `ul` / `table` / `note` / `key` / `pitfall` / `code` / …），
由 `Blocks.astro` 统一渲染。

## 理由

1. **结构一致性从「靠脚本比对」升级为「类型上不可能违反」**。
   中英写在同一行相邻位置，不可能出现「中文三段、英文两段」。
   `{ zh, en }` 缺一边就是编译错误。
2. **代码块天然一字不差**。代码只写一次（`code: string`），
   中英只翻译它的说明文字 —— 而 MDX 方案里代码要复制两份，早晚会漂移。
3. **渲染统一**。全站排版节奏由一个组件保证，不会因为某篇 MDX 手写了奇怪的标记而破相。
   讲布局的站点尤其不能容忍这个。
4. **id 可被类型约束**。`demo.id`、`theory[]` 都能在构建期校验。

## 代价

- 作者不能随手写任意 HTML。**这正是我们想要的约束** —— 块类型词汇表覆盖了样例里出现的全部结构。
- 需要维护一个渲染器（`Blocks.astro`，约 120 行）。一次性成本。

## 仍然保留的设计

Zod 校验（`content/schema.ts`）与 parity 脚本都保留了，只是检查对象变了：
Zod 现在直接校验结构化对象，脚本负责类型管不到的部分（漏译、篇幅比、引用有效性、演示注册）。
